# 현재 장비의 Geo 조회 성능 개선 3회 반복

## 목표와 범위

사용자 요청에 따라 원인 발굴 → 개선 → 정확성·성능 검증을 세 차례 수행한다. 장비·서버 증설 없이 현재 장비에서 비교하며, 검토만으로 완료 처리하지 않는다. 운영 데이터의 재적재나 PostgreSQL·RustFS의 구동·정지·재시작은 수행하지 않는다.

기준 소스는 `289353f50bf7892afd18b5b564cc93a887259969`다. 기존 완료 DB를 보존하고, 서빙 SQL·캐시·필요한 조회 인덱스를 대상으로 한다. v1 호환 응답, v2의 후보·정확한 total·정렬·좌표 NULL·정상 릴리스 지문을 유지한다.

## 확인한 근거

- 2026-11-07 운영 메타데이터: ARM 4코어·약 7.5GiB RAM, API 메모리 한도 1.5GiB·공용 PostgreSQL 한도 3GiB. PostgreSQL 18.6의 shared_buffers는 768MiB다.
- `mv_geocode_target`과 `mv_geocode_text_search`의 테이블·인덱스 합계는 약 7.5GiB다. MV의 all-visible 비율은 이미 약 99.98%다.
- `GeoCacheRepository.get_json()`은 적중 때마다 같은 행을 UPDATE한다. search에는 결과 캐시가 없고 정확한 전체 건수를 계산한다.
- 운영의 EXPLAIN에서 지역 조건 없는 reverse는 GiST KNN, 법정동 조건을 넣은 reverse는 지역 후보의 Bitmap Heap Scan·정렬을 선택했다. 반경 조건은 현재 KNN 후보를 얻은 뒤 적용한다.
- `강남` 같은 짧은 검색의 EXPLAIN은 text-search MV의 Seq Scan·JIT를 포함한다. 도로명 전체 주소는 도로명과 시군구 인덱스를 BitmapAnd한 뒤 본번·부번·지하 여부를 필터링한다.
- pg_stat_statements는 2026-10-27 이후 누적이며 이전 벤치마크·이전 코드의 기록을 포함할 수 있다. 이 평균을 현재 QPS나 p95로 해석하지 않는다.
- CodeGraph MCP는 현재 Linux worktree 경로를 읽지 못해 Linux CLI의 기존 인덱스로 context·status를 확인했다. 새 초기화나 Windows CodeGraph 실행은 하지 않았다.

## 실행 순서

### 1회차 — 역지오코딩 후보 축소

1. 기존 쿼리와 반경을 조기에 적용한 후보의 실행계획·결과를 비교한다.
2. 후보 단계에 인덱스로 처리할 수 있는 반경 조건을 적용한다. 필요한 경우 기존 후보 수·경계·동률 처리를 보완한다.
3. 지역 조건 유무·빈 결과·경계·같은 좌표의 여러 주소에서 결과·정렬을 비교한다.
4. 같은 장비의 교차 순서 비교로 시간과 읽은 블록을 기록한다. 실패한 검증은 그 단계의 진단을 보존하고 재개한다.

### 2회차 — 반복 조회의 DB 왕복·쓰기 축소

1. 1회차 뒤 반복 조회에서 남은 비용을 측정한다.
2. 현재 릴리스와 전체 조회 옵션에 종속된 메모리 캐시, 동일 요청의 중복 실행 방지, 캐시 적중의 DB 쓰기 축소를 비교해 필요한 최소 변경을 적용한다.
3. 캐시 용량·만료·릴리스 전환·동시 요청·취소·응답 격리와 기존 관측 의미를 확인한다.
4. 반복 키와 고유 키를 구분해 적중률·DB 호출·쓰기·응답시간·메모리를 비교한다.

### 3회차 — 남은 실제 병목 재발굴

1. 앞선 변경의 결과를 기준으로 우선순위를 다시 정한다.
2. 정확 주소 복합 인덱스, 검색어 사전·좁은 MV·지연 상세 조회, SQL 계획 분리, geometry 처리 중 효과가 검증되는 후보를 선택한다.
3. 인덱스·서빙 산출물이 필요하면 기존 데이터에서 생성하고 기존 정합성·좌표 판정을 보존한다. 원천 적재부터 다시 시작하지 않는다.
4. 최종 개선의 정확성·성능과 이전 회차의 회귀를 확인한다.

## 판단 기준과 기록

- 회차마다 원인·변경 파일·검증 방법·수정 전후 측정값·남은 한계를 남긴다.
- 일반 조회와 geometry 포함 조회, 반복·고유 요청, 지역 조건 유무를 분리한다.
- p50·p95·p99·처리량·오류·거절·DB 왕복·읽기·쓰기·RSS를 함께 평가한다. 대기나 오류를 제외해 속도를 좋게 보이게 하지 않는다.
- 코드·SQL의 결과가 같은지 먼저 확인하고, 실행계획의 추정 비용을 실제 실행시간으로 표기하지 않는다.
- 현재 데이터·장비에서 반복 측정되지 않은 개선 배수를 약속하지 않는다.
- 최종 WSL ext4 필수 게이트, 필요한 실제 DB 검사, 비밀값 감사, 정확한 최종 HEAD의 CI·10분 리뷰 창을 통과한 뒤 병합한다. 이미지 반영은 운영 런북의 정식 절차와 공용 잠금을 따른다.

### 2회차 검증과 수정

- 같은 ARM API 컨테이너에서 후보 소스를 별도 프로세스로 실행했다. 메모리 캐시만 끈 경로와 켠 경로를 before→after→after→before로 비교했다. 8종·각 변형 24개 표본이며 초기화·HTTP 인증·전송은 제외했다. 운영 API의 실행 코드를 덮어쓰지 않았다.
- 반복 적중 구간의 DB 명령은 0회다. 비어 있는 메모리 캐시에 같은 키 32건을 동시성 8로 요청하면 영속 캐시 UPDATE는 32→1회다. 첫 요청·고유 입력과 공개 API 인증의 DB 비용은 남는다. 고유 입력 표본에서는 지연 개선을 주장하지 않는다.
- 처음 실측에서 발견한 `query_id` 재사용은 캐시 보관 대상에서 제외해 고쳤다. 호출마다 새 값을 발급하고 응답 내용 비교에서는 이 추적 식별자만 제외했다. 실패·보조 geometry timeout은 보관하지 않는다.
- 5만 고유 결과의 보관 예산은 67,107,744바이트로 64MiB 이내였다. 직렬화 버퍼가 표시 크기보다 큰 내부 할당을 유지하던 문제를 복사로 해결해 최고 RSS를 약 670→148MiB로 낮췄다. RSS와 캐시 예산은 다른 값이다. 종료 후 계산상 보관량은 0이다.
- 전체 pytest 2,070개·Ruff·엄격 mypy를 통과했고, 버퍼 수정 뒤 집중 검사 20개를 다시 통과했다. 독립 PostGIS DB의 실제 릴리스 전환·늦은 이전 릴리스 캐시 쓰기 검사 3개도 통과했다. 권한이 필요한 확장은 소유 표식을 확인한 독립 테스트 DB에만 준비했다.
- [ADR-075](../adr/075-bounded-memory-result-cache.md)에 용량·TTL·릴리스 키·취소·응답 격리·관측 의미를 기록했다. 수치는 전체 운영 p95나 QPS 보장이 아니다.

### 3회차 검증과 수정

- 캐시를 우회한 정확 도로명주소의 같은 SQL 14종을 인덱스 생성 전후로 비교했다. 변형별 16개 표본의 결과·좌표·정확한 total이 같고 오류 0이다. 모든 계획이 새 인덱스를 선택했다. 서버 실행·버퍼 접근과 왕복을 포함한 SQL 호출 시간을 구분해 정본에 기록했다.
- 운영에 추가한 인덱스는 291,987,456바이트(약 278.5MiB)이며 최종 성공한 생성 1회는 187.296초였다. 실패·원인 분석·재시도 대기는 이 시간과 구분한다. maintenance_work_mem 64MiB·병렬 유지보수 worker 0으로 제한했고 MV 물리 식별자를 보존했다. 인덱스 크기를 RAM 상주량으로 해석하지 않는다.
- MV가 지원하지 않는 사전 LOCK 구문을 제거하고 DDL 자체의 잠금을 사용했다. 로케일 정렬 후보의 진행이 오래 걸려 소유 PID·SQL을 확인한 뒤 해당 작업만 취소했다. 동등 비교를 지원하는 text_pattern_ops로 바꾸고 실제 PostGIS 검사와 마이그레이션 왕복을 다시 통과했다.
- 생성 후 검증기의 추정 행 수 동일성 조건 때문에 롤백한 시도는 보존했다. 통계 추정치는 바뀔 수 있으므로 MV 물리 식별자·인덱스 유효성·결과 동일성으로 고쳐 인덱스 생성부터 재개했다. 원천 적재·MV 재생성을 반복하지 않았다.
- 빈 결과 일부와 전체 왕복 시간에는 악화 표본도 남는다. 예를 들어 지역 없는 search의 실행 8.579→8.739ms도 그대로 기록했다. 물리 인덱스 생성 전후 비교이므로 AB 교차 순서 실험으로 표기하지 않는다.

## 최종 코드 검사

WSL ext4에서 pytest 2,071개 통과·선택 환경 검사 234개 생략, Ruff·엄격 mypy 171개 파일·의존 계약 1개·OpenAPI 보존 검사를 통과했다. 실제 독립 PostGIS에서는 쿼리·인덱스 16개와 릴리스 전환 3개가 통과했고 마이그레이션 upgrade→downgrade→upgrade도 통과했다. Linux CodeGraph sync/status는 최신이다.

전용 security-review 스킬은 설치되어 있지 않아 직접 변경 diff·인증 선행 경계·가변 응답 격리·취소·유한 메트릭 label을 검토했다. 스테이징과 추적 파일의 실제 운영 키 일치는 0이다.

정확한 최종 HEAD a204ccc의 CI 5개와 10분 리뷰 창·의견 3면을 확인해 #626을 3e3da65로 병합했다. 병합 전후 소스 트리는 같았다. 새 ARM 이미지의 API 171개·코드 서버 187개 소스와 의존성·요청 공유·응답 격리·실제 API 시작 명령·마스킹은 통과했다. 현재는 공식 Manager 공용 잠금을 기다리며 운영 이미지 교체와 이후 실제 UI 검증은 아직 완료하지 않았다.

추가 MV·비정규화·캐시 서버·covering index·인덱스 정리·pool·예열·파티션을 비교한 판단은 [검토 문서](../reviews/current-hardware-read-performance.md)에 정리했다. 짧은 검색어의 첫 조회 비용과 공개 API 인증·고유 입력의 DB 비용은 남는다.

## bbox 호환성 보완과 최종 배포 준비

공용 잠금 대기 중 기존 SDK의 NaN·무한값·딕셔너리 bbox를 검사해 회귀를 수정했다. 검증된 입력을 캐시 키와 조회에 함께 사용하고 비유한 값은 최종 응답 캐시만 우회한다. 최종 집중 32개·전체 2,082개·정적 검사를 통과했다. #628의 정확 a1bc731에서 CI 5개·10분 리뷰 창·의견 3면을 재확인해 5c4f842로 병합했다.

이전 3e3 이미지 교체 전 내 대기만 취소하고 새 ARM 이미지를 만들었다. 소스 171개·코드 서버 합계 187개와 의존성·캐시·bbox·시작 명령·마스킹을 검증했다. 기존 정상 데이터셋·유효 인덱스·유휴 상태도 재확인했다. 새 이미지로 공식 공용 잠금을 기다리며 운영 교체·이후 실제 UI·Wiki는 아직 완료하지 않았다. 과거 이미지 준비 근거와 배포 전 HTTP 기준값은 정본 delivery에 보존한다.
